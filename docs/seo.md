# SEO

**Site Settings → SEO** controls how the site shows up in search results and in
link previews. Everything on the tab is optional; a blank field is left out of
the page rather than filled with a guess.

## Site URL

The full `https://` address of the site, e.g. `https://example.com` (include a
path if ghoti lives in a subdirectory). Canonical links, `og:url`, `og:image`,
structured data, and the sitemap all need absolute URLs, and they are built
**only** from this setting — or from `GHOTI_PUBLIC_URL` when it is blank —
never from the request's `Host` header, which a visitor controls. With neither
set, those tags are omitted.

## What goes into every page's `<head>`

Emitted by `ghoti.header.php`, which every theme includes, from
`ghoti.seo.php`:

| Tag | Source |
|---|---|
| `<title>` | Home: **Home page title**, or the site title. Other pages: **Other page titles** with `{page}` and `{site}` replaced (default `{page} \| {site}`). The page name comes from **Manage Pages**. |
| `meta description` | **Site description** (up to 300 characters; aim for 150–160). Themes that ship their own description use it only while this is blank. |
| `meta keywords` | **Keywords** — harmless, but most search engines ignore it. |
| `meta robots` | `index, follow`, or `noindex, nofollow` when indexing is off, for private pages, unknown page ids, and the HTML sitemap view. |
| `link rel=canonical` | `SiteURL/` for home, `SiteURL/?page=N` for a public page. |
| Open Graph / Twitter card | Site name, title, description, URL, **Share image** (a local image path; about 1200×630 works everywhere), **Twitter/X handle**. |
| Verification | **Google** (`google-site-verification`) and **Bing** (`msvalidate.01`) codes — paste the `content` value only, not the whole tag. |
| JSON-LD | schema.org `WebSite` and `Organization` (name from **Legal operator name** on the Identity tab, logo from the header image), when **Publish structured data** is on. |

A private page reports nothing about itself: its title is never put in the
`<head>`, where a signed-out visitor could read it.

## Crawlable navigation

Page menu links carry a real `href="?page=N"`, so crawlers can follow them.
Clicking one still loads the page in place, and the address bar now updates to
match, so a page can be bookmarked, shared, and reached with Back.

## robots.txt and sitemap.xml

Both are generated by `seo.php` and served at the site root by rewrite rules in
`.htaccess` (needs `mod_rewrite` and `AllowOverride`). Without them they are
still at `seo.php?file=robots` and `seo.php?file=sitemap`. Search engines only
look for `robots.txt` at the root of the host, so an install in a
subdirectory needs the host's own `robots.txt` to point at the sitemap.

- **robots.txt** disallows the password-reset and backup scripts,
  appends **Extra robots.txt rules** (only `User-agent`, `Allow`, `Disallow`,
  `Crawl-delay` and `Sitemap` lines are accepted — e.g. to block AI crawlers),
  and names the sitemap when there is a Site URL.
- **sitemap.xml** lists the home page once (as the site root), every other
  public page, and the privacy and accessibility notices. Private pages are
  never listed. It answers 404 without a Site URL or while indexing is off.

Submit `SiteURL/sitemap.xml` in Google Search Console and Bing Webmaster Tools.

## Turning indexing off

Unticking **Let search engines index this site** marks every page `noindex`
and adds an `X-Robots-Tag: noindex, nofollow` header. It deliberately does
*not* add `Disallow: /` to robots.txt: a crawler that may not fetch a page
never sees its `noindex`, and can still list the bare URL from links
elsewhere.

## Not done here

Page bodies are still loaded by JavaScript after the page shell arrives.
Google renders JavaScript, but some crawlers and link-preview bots do not and
will see only the `<head>` metadata. Server-rendering page content is a
separate change: `getPage()` records a view and adds the admin edit block, so
it cannot simply be called while the shell is being built.

`tests/seo.php` covers all of the above.
